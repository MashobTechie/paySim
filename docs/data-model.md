## 1. Conventions

- **Identifiers.** UUIDv7, generated by the database function `simconfig.uuidv7()` (C8).
  Synthetic operators use readable text IDs (`ops-01`).
- **Run ownership.** Every simulation-owned record has a non-null `simulationRunId` (D14),
  including child records. Run-consistent references are composite:
  `(childFk, simulationRunId) → parent(id, simulationRunId)`.
- **Money.** `BIGINT` minor units plus a `CHAR(3)` ISO 4217 currency (C1). Never decimal or
  float. Positive-amount and currency-format checks are enforced in the database.
- **Time.**
  - Business times (received, verified, settled…) are written by the application from the
    run's clock, which is simulated in replays.
  - Leases, lock-related times and `createdAt` audit stamps use database time.
- **Mutability classes:**

  | Class           | Rule                                                                                                                      |
  | --------------- | ------------------------------------------------------------------------------------------------------------------------- |
  | **Insert-only** | No `UPDATE` or `DELETE`, enforced by trigger and by grants.                                                               |
  | **Controlled**  | Only the listed columns may change. Enforced by column-level `UPDATE` grants, plus triggers that check legal transitions. |
  | **Catalogue**   | Global configuration, written by the schema owner only. Never modified once published.                                    |

**Both previously open entity questions are resolved:**

- `SimulatedBank` is a run-owned, frozen copy of a bank definition (DM2).
- `AnomalyEvidence` is stored as separate insert-only rows (DM8).

**Deliberately absent:** a claim-allocation record (allocation is computed under the claim
lock), any ledger, an event-sourced payment log, a separate replay-run entity, and actor or
user entities. Operators are an allowlist, not accounts.

## 4. Global catalogue (`simconfig`)

### 4.1 `ConfigurationProfile`

- **Purpose:** a named family of simulation configurations (DM2).
- **Data:** name, description.
- **Uniqueness:** `name`.
- **Relationships:** has many versions.

### 4.2 `ConfigurationProfileVersion`

- **Purpose:** an immutable, complete configuration that runs pin (DM2, I20).
- **Data:** version number, content hash, event-processing retry limit and back-off base,
  processing lease, poll lease, **failure-injection rules** (a versioned configuration
  document; its structure is defined in the failure-injection phase), publication time.
- **Uniqueness:** `(profileId, versionNo)`.
- **Relationships:** has many bank definitions; pinned by many `SimulationRun`s.
- **Protects:** reproducibility. A test result traces to the exact rules that produced it.

### 4.3 `ConfigurationBankDefinition`

- **Purpose:** one simulated bank's declared behaviour within a version.
- **Data:** provider code, settlement window _W_, acceptance TTL, escalation threshold,
  automatic retry limit and back-off schedule (D4), whether the queryability guarantee is
  declared (N1).
- **Uniqueness:** `(profileVersionId, providerCode)`.

### 4.4 `SyntheticOperator` and 4.5 `SyntheticOperatorPermission`

- **Purpose:** the server-side allowlist of seeded synthetic identities and their permitted
  actions (D32, I22). This is **not authentication**: it is suitable for a controlled
  simulator or demo only.
- **Data:** operator ID (text), display name, active flag; permission rows
  `(operatorId, action)`.
- **Uniqueness:** operator ID; `(operatorId, action)`.
- **Protects:** a client-supplied actor never grants authority by itself. Database triggers
  check permissions on accepted commands, approvals, critical resolutions and manual attempt
  resolutions.

## 5. Runs and run configuration (`paysim`)

### 5.1 `SimulationRun`

- **Purpose:** the isolation boundary and owner of every simulation record (D14, D34).
- **Data:**
  - run reference (`RUN-0001`);
  - type (`SCENARIO` or `REPLAY`) and source run (replays only);
  - status (`CREATED`, `ACTIVE`, `COMPLETED`, `ABORTED`) and the `diverged` marker;
  - pinned configuration version;
  - **frozen settings:** event retry limit, back-off, processing lease, poll lease;
  - simulated clock position (replays);
  - lifecycle timestamps.
- **Relationships:** owns everything run-scoped. `sourceRunId` → `SimulationRun` is cross-run
  exception 1 (L3).
- **Uniqueness:** `runReference`; `(id, sourceRunId)`, which divergences reference.
- **Mutability:** controlled.
  - Status follows `CREATED → ACTIVE → COMPLETED`, plus `CREATED|ACTIVE → ABORTED`.
  - `diverged` can only go `false → true`, and only on replays.
  - Settings and the pinned version never change.
  - `COMPLETED` requires no in-flight work.
- **Protects:** C6, I8, I20.

### 5.2 `SimulatedBank`

- **Purpose:** the run's frozen copy of a bank definition, plus per-run secrets (DM2).
- **Data:** provider code, _W_, acceptance TTL, escalation threshold, retry limit and
  back-off, guarantee flag, **signing secret** (synthetic, per run), **ingress key hash**
  (SHA-256 of a cryptographically random key; the plaintext is never stored PaySim-side; D29).
- **Uniqueness:** `(simulationRunId, providerCode)`; `ingressKeyHash` (global);
  `(id, simulationRunId)`.
- **Mutability:** insert-only, and only while the run is `CREATED`. In a replay, parameters and
  secret must equal the source run's.
- **Protects:** §5.7 (N1–N3) and D4. Values can't drift mid-run.

## 6. Claims and recipients (`paysim`)

### 6.1 `Claim`

- **Purpose:** the authoritative approved payable amount, and the allocation lock target (Q3,
  D11).
- **Data:** claim reference, approved payable amount, currency, `approvedForPayout`,
  description.
- **Uniqueness:** `(simulationRunId, claimRef)`; `(id, simulationRunId)`.
- **Mutability:** controlled. Only `approvedForPayout` may change. That column grant also
  makes `SELECT … FOR UPDATE` possible for the app role.
- **Protects:** I9. The payment-insert trigger takes this row's lock and checks allocation.

### 6.2 `Recipient`

- **Purpose:** a reusable payee profile (Q2, DM10).
- **Data:** bank code, account number, account name, creating command.
- **Uniqueness:** `(simulationRunId, bankCode, accountNumber)`; `(id, simulationRunId)`.
- **Mutability:** controlled. Only `accountName` (and `updatedAt`) may change, via
  `UPDATE_RECIPIENT` commands, which are the audit trail (A8 resolved).

## 7. Payments (`paysim`)

### 7.1 `Payment`

- **Purpose:** the business intention, with its current status (C2, C3).
- **Data:**
  - reference (`PAY-2026-000042`) and type (`CLAIM_PAYOUT`);
  - claim, amount, currency;
  - status (the nine states) and `version`;
  - current snapshot;
  - creator actor and creating command;
  - `retryOf`;
  - `nextDispatchAt` (DM11).
- **Uniqueness:** `(simulationRunId, reference)`; `(id, simulationRunId)`.
- **Mutability:** controlled. Only status, `version` (+1 per update), current snapshot,
  `nextDispatchAt` and `updatedAt` may change.
  - Every status change must be a legal §4.1 transition.
  - At commit, the status must equal the latest `PaymentTransition`'s target (I5), and a
    current snapshot must exist.
- **Protects:** I4, I5, I9, I12.

### 7.2 `RecipientSnapshot`

- **Purpose:** the immutable recipient details for one payment (D12).
- **Data:** snapshot number, optional source recipient, bank code, account number, account
  name, creating command.
- **Uniqueness:** `(paymentId, snapshotNo)`; `(id, simulationRunId)`.
- **Mutability:** insert-only.

### 7.3 `VerificationResult`

- **Purpose:** the definitive outcome of verifying one snapshot (§6.2). Transient verifier
  errors leave only bank interactions.
- **Data:** snapshot; bank request and response; outcome (`MATCH`, `TOKEN_MISMATCH`,
  `EMPTY_NAME`, `ACCOUNT_NOT_FOUND`, `ACCOUNT_NOT_OPEN`); both raw names and token lists;
  failure reason; disposition (`APPLIED` or `STALE_SNAPSHOT`); verified time.
- **Uniqueness:** `(id, simulationRunId)`.
- **Mutability:** insert-only.

### 7.4 `Approval`

- **Purpose:** what finance approved, exactly (§6.3).
- **Data:** payment, snapshot, verification result, amount, currency, approver, command, time.
- **Uniqueness:** `paymentId` (at most one per payment); `(id, simulationRunId)`.
- **Mutability:** insert-only. A trigger enforces the following:
  - snapshot = payment's current snapshot;
  - verification is a `MATCH`/`APPLIED` result for that snapshot;
  - amount and currency = the payment's;
  - approver ≠ creator (D8);
  - the approver has `APPROVE_PAYMENT`.

### 7.5 `PaymentAttempt`

- **Purpose:** one instruction to a bank (§5).
- **Data:**
  - attempt number, provider, bank reference, status (six values);
  - approval, snapshot, amount, currency (all copied from the approval);
  - acceptance deadline;
  - polling fields: `nextStatusQueryAt`, `statusQueryCount`, `earliestQualifyingQueryAt`,
    `escalateAt`, `escalatedAt`, `pollClaimToken`, `pollLeaseExpiresAt`, `pollGeneration`.
- **Uniqueness:**
  - `(paymentId, attemptNumber)`;
  - `(simulationRunId, providerCode, bankReference)`;
  - **partial:** `(paymentId)` where status ∈ {`PENDING`, `SUBMITTED`, `UNKNOWN`} (I1);
  - `(id, simulationRunId)`.
- **Mutability:** controlled. Status follows §5.2 only, and resolved statuses are final.
  Polling claims follow §5.8. At commit, status = the latest `AttemptStatusChange` target.
  Insert is blocked while a critical anomaly is open for the payment (D15).
- **Protects:** I1, I17, I23.

### 7.6 `AttemptStatusChange`

- **Purpose:** append-only attempt history, with cause (§5.2, I13).
- **Data:** sequence number, from and to status, typed cause (bank response, provider event,
  inbound command, or system job), actor.
- **Uniqueness:** `(attemptId, sequenceNo)`; `(id, simulationRunId)`.
- **Mutability:** insert-only. A command cause requires `RESOLVE_ATTEMPT` permission, and only
  `SUCCEEDED` or `FAILED_PERMANENT` targets (R8).

### 7.7 `PaymentTransition`

- **Purpose:** one row per accepted payment state change (I5).
- **Data:** sequence number, from and to status, trigger, typed cause, related attempt,
  actor, reason.
- **Uniqueness:** `(paymentId, sequenceNo)`; `(id, simulationRunId)`.
- **Mutability:** insert-only. `(from, trigger, to)` must be one of the 14 §4.1 transitions,
  and `from` must equal the previous row's `to`.

### 7.8 `Settlement`

- **Purpose:** the single financial effect (D10, I2).
- **Data:** payment, succeeded attempt, amount, currency, typed cause, settled time.
- **Uniqueness:** `paymentId`.
- **Mutability:** insert-only. A trigger requires the attempt to be `SUCCEEDED` and to belong to
  the payment, and the amount and currency to equal the attempt's.

## 8. Commands and idempotency (`paysim`)

### 8.1 `InboundCommand`

- **Purpose:** the audit log and replay input tape (§9.1).
- **Data:**
  - command type, API version, actor, request ID;
  - idempotency key, request fingerprint, canonical payload;
  - target payment and claim;
  - outcome (`ACCEPTED`, `REJECTED`, `IDEMPOTENT_REPLAY`), rejection code and message;
  - original command (replays only);
  - resulting payment reference (D18);
  - received time.
- **Uniqueness:** `(id, simulationRunId)`.
- **Mutability:** insert-only. A trigger requires accepted commands to come from an active
  allowlisted operator with the matching permission (I22).

### 8.2 `IdempotencyRecord`

- **Purpose:** binds one outcome to a key (D28, I3).
- **Data:** actor, key, fingerprint, command type, API version, outcome, rejection code
  (deterministic codes only), response status and body, command.
- **Uniqueness:** `(simulationRunId, actorId, idempotencyKey)`.
- **Mutability:** insert-only. A trigger checks that the record matches its command.

---

## 9. Provider events and webhooks (`paysim`)

### 9.1 `ProviderEvent`

- **Purpose:** the logical fact, recorded once (§8.1).
- **Data:**
  - provider, provider event ID, type, bank reference, amount, currency, canonical payload and
    hash, first-received time;
  - **processing fields:** status, attempt count, claim token, lease owner and expiry, next
    attempt time, last error, requeue generation, outcome and reason, processed time, resolved
    attempt and payment.
- **Uniqueness:** `(simulationRunId, providerCode, providerEventId)`; `(id, simulationRunId)`.
- **Mutability:** controlled. Identity and payload are immutable. A trigger enforces the §8.5
  state machine:
  - a claim increments the count, issues a new token and respects the limit;
  - finalisation keeps the token;
  - a requeue resets the count and increments the generation;
  - `PROCESSED` is final.

### 9.2 `WebhookDelivery`

- **Purpose:** one durably received HTTP delivery (receipt only).
- **Data:** provider, received time, selected headers, raw body (≤ 64 KiB, checked), body hash,
  signature validity, receipt outcome, HTTP status, linked event.
- **Uniqueness:** `(id, simulationRunId)`.
- **Mutability:** insert-only. Checks tie each outcome to signature validity and event linkage.

### 9.3 `EventProcessingAttempt`

- **Purpose:** the log of ended processing attempts (§8.5).
- **Data:** event, claim token, worker, claimed and ended times, result (`COMPLETED`,
  `TECHNICAL_ERROR`, `LEASE_EXPIRED`), error.
- **Uniqueness:** `(providerEventRecordId, claimToken)`.
- **Mutability:** insert-only.

## 10. Bank interactions (`paysim`)

### 10.1 `BankInteractionRequest`

- **Purpose:** every question asked of a bank, recorded before the call (D17, D27).
- **Data:** provider, type, typed subject (snapshot or attempt), readable key, occurrence
  number, poll generation (status queries), canonical payload and hash, sent time.
- **Uniqueness:**
  - `(simulationRunId, providerCode, interactionType, readableKey, occurrenceNo)` (DM7);
  - **partial:** `(subjectAttemptId, pollGeneration)` for `STATUS_QUERY` (I23);
  - `(id, simulationRunId)`.
- **Mutability:** insert-only. Occurrence numbers must be gap-free. A status query must carry
  the attempt's current poll generation while a poll claim is held.

### 10.2 `BankInteractionResponse`

- **Purpose:** the bank's answer, or an observed timeout.
- **Data:** request, received time, kind (`RESPONSE` or `NO_RESPONSE`), HTTP status, body,
  signature validity, classification, elapsed time.
- **Uniqueness:** `requestId`; `(id, simulationRunId)`.
- **Mutability:** insert-only. A request with no response row is "unanswered", which is
  distinct from `NO_RESPONSE`.

## 11. Anomalies (`paysim`)

### 11.1 `Anomaly`

- **Purpose:** a recorded contradiction (§10.4).
- **Data:** type, severity (fixed), evidence key, status (`OPEN` or `RESOLVED`), last action
  sequence number, linked payment, attempt and event, related anomaly, detector, detected time,
  creating transaction ID.
- **Uniqueness:** `(simulationRunId, anomalyType, evidenceKey)`; `(id, simulationRunId)`.
  Partial index `(paymentId)` for open critical anomalies.
- **Mutability:** controlled. Only status and last action sequence number may change. At
  commit, they must match the latest action, and the anomaly must have an `OPENED` action and
  at least one evidence row.

### 11.2 `AnomalyEvidence`

- **Purpose:** the immutable evidence set (I16).
- **Data:** a typed reference to a provider event, delivery, bank request, bank response,
  attempt status change, or processing attempt.
- **Uniqueness:** one row per anomaly and evidence record.
- **Mutability:** insert-only, and only in the transaction that created the anomaly.

### 11.3 `AnomalyAction`

- **Purpose:** the append-only anomaly history.
- **Data:** sequence number, action (`OPENED`, `RESOLVED`, `REOPENED`, `NOTE_ADDED`), actor,
  typed cause, reason, resolution type, follow-up reference.
- **Uniqueness:** `(anomalyId, sequenceNo)`.
- **Mutability:** insert-only. A trigger enforces D25: critical anomalies are resolved only by
  a user with `RESOLVE_CRITICAL_ANOMALY` via a command. System resolution applies only to
  Attention anomalies, with `CONDITION_CLEARED`.

## 12. Replay (`paysim`)

### 12.1 `ReplayDivergence`

- **Purpose:** each way a replay differs from its source (§9.2, §9.4).
- **Data:** type, deterministic key, typed source references (command, delivery, event,
  request), typed replay references, both payload hashes, detail.
- **Ownership:** the replay run. Source references are composite with `sourceRunId`, which must
  be the replay's own source. This is cross-run exception 2 (L3).
- **Uniqueness:** `(simulationRunId, divergenceType, divergenceKey)`.
- **Mutability:** insert-only. An insert sets the run's `diverged` marker.

## 13. Simulated bank (`simbank`, D31)

The bank side has no foreign keys into PaySim-side records except the run itself (the shared
ownership root). The two sides correlate only by bank reference and provider event ID.

### 13.1 `BankRunProfile`

- **Purpose:** the bank's own copy of its run configuration.
- **Data:** provider code, _W_, acceptance TTL, signing secret, webhook ingress key (the bank's
  configured endpoint; bank-side only).
- **Uniqueness:** `(simulationRunId, providerCode)`.
- **Mutability:** insert-only, while the run is `CREATED`.

### 13.2 `SimulatedBankAccount`

- **Purpose:** accounts the bank knows about, used for verification and permanent failures.
- **Data:** account number, holder name, status (`OPEN`, `CLOSED`, `DORMANT`).
- **Uniqueness:** `(simulationRunId, providerCode, accountNumber)`.
- **Mutability:** insert-only.

### 13.3 `BankInstruction`

- **Purpose:** each instruction the bank received (accepted-instruction state, DM3).
- **Data:** bank reference, acceptance deadline, received time, settlement window (copied),
  `visibleAt`, amount, currency, destination, status (`RECEIVED`, `PROCESSING`, `SETTLED`,
  `FAILED`, `REFUSED_LATE`), failure code, planned outcome.
- **Uniqueness:** `(simulationRunId, providerCode, bankReference)`.
- **Mutability:** controlled (status progression only). Checks enforce two rules:
  - **late refusal:** `REFUSED_LATE` ⇔ received after the deadline;
  - **queryability:** `receivedAt ≤ visibleAt ≤ receivedAt + W`.

### 13.4 `BankWebhookDispatch`

- **Purpose:** webhooks the bank plans or has sent, including deliberate duplicates.
- **Data:** provider event ID, send number, bank reference, event type, payload, scheduled and
  sent times, HTTP status.
- **Uniqueness:** `(simulationRunId, providerCode, providerEventId, sendNo)`.
- **Mutability:** controlled. Only `sentAt` and `httpStatus` may be set, once.

## 14. Relationship summary

- **Runs and configuration.** A run pins one configuration version (global), materialises its
  simulated banks, and owns everything else. A replay run points to its completed source run.
- **Claims and payments.** A claim has many payments. Live payments never exceed the claim's
  approved amount. A payment has many snapshots and points to the current one. It has at most
  one approval, many attempts (at most one unresolved), many transitions and at most one
  settlement.
- **Attempts.** Each attempt is built from the approval. Its status changes are logged, each
  with a cause.
- **Commands.** Commands are the input tape. Each idempotency key binds exactly one recorded
  outcome.
- **Webhooks.** A provider event has many deliveries and many processing attempts. The event
  row holds the live claim.
- **Bank interactions.** Each bank request has at most one response, which points back to it.
- **Anomalies.** An anomaly carries fixed evidence and append-only actions; its stored status
  mirrors the latest action.
- **Divergences.** A divergence belongs to a replay run and points at its source run's records.
- **The bank side.** The bank keeps its own accounts, received instructions and planned
  webhooks, and is reachable only through recorded interactions and webhooks.
